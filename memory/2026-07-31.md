## Keycloak Login Failures (2026-07-31 ~17:20 UTC)

**Problem:** Neither admin nor yappingboy can log into Keycloak admin console from the web UI.

**Findings:**
1. **Keycloak pods are running** (keycloak-0 and keycloak-1 are Running)
2. **Local admin login works** — tested via Keycloak internal port 8080:
   - `curl -s -X POST http://keycloak-1.keycloak.identity.svc:8080/realms/master/protocol/openid-connect/token -d "username=admin&password=***&grant_type=password" -H "X-Forwarded-Host: keycloak.identity.svc:8080"` → returns access_token (expires in 60s)
3. **yappingboy also works via local login:**
   - `curl ... username=yappingboy&password=***` → also returns access_token
4. **But web login fails** — admin console at `keycloak.becklab.cloud` returns 500

**Root cause investigation:**
- Web login uses `/admin/master/console/` which requires SSO chain: traefik → oauth2-proxy → keycloak-forwardauth → keycloak
- SSO chain uses `sso-admin-chain` middleware with oauth2-proxy
- oauth2-proxy authenticates against Keycloak master realm → validates user → passes to Keycloak admin console
- **The admin console web login fails with 500** — likely oauth2-proxy or keycloak-forwardauth is broken

**Additional discovery:**
- LLDAP admin user password: set to `y4pp1ngb0y` via `LLDAP_LDAP_USER_PASS` env var
- LLDAP admin password was updated on July 28 (password hash created 2026-07-28T16:38:06.707Z)
- yappingboy credentials were modified July 28 (hash created 2026-07-28T16:38:06.862Z)
- Both users are LDAP-federated (federated identity → LLDAP)
- The password `y4pp1ngb0y` works locally in Keycloak for both users, but the **web admin console login fails**

**Possible causes:**
1. oauth2-proxy session/token validation issue
2. Keycloak admin console cookies/domain mismatch
3. LLDAP bind DN password mismatch (LLDAP_LDAP_USER_PASS may not match actual LLDAP admin password)
4. Keycloak admin user has a local password credential (separate from LDAP)

**Next steps:**
- Check oauth2-proxy logs for errors during admin console login
- Check keycloak-forwardauth logs
- Test admin console login flow manually (cookie-based)
- Verify LLDAP admin password matches what Keycloak uses for LDAP bind
- Check if Keycloak admin user has a local password credential (separate from LDAP)

## Keycloak Admin API Scopes Discovery (2026-07-31 ~17:36 UTC)

**Problem:** Even with valid access token from `admin-cli` password grant, admin API calls return 401.

**Findings:**
1. **Admin token works for `/userinfo`** — `curl -H "Authorization: Bearer <token>" https://keycloak.becklab.cloud/realms/master/protocol/openid-connect/userinfo` returns user info successfully.
2. **Admin token fails for admin API** — `curl -H "Authorization: Bearer <token>" https://keycloak.becklab.cloud/admin/master/console/` returns 401.
3. **`/admin` endpoint returns 403** (not 401) — means user is authenticated but lacks required roles for that namespace.
4. **Token introspection** shows:
   - `scope: email profile roles openid`
   - `realm_access.roles: [default-roles-master, offline_access, admin]`
   - `client_roles` only has `roles` (not `admin-cli` roles)
   - **Token is valid** but admin API requires specific scope or client
5. **`roles` client scope has `"include.in.token.scope": "false"`** — this means roles are included in the token but the `roles` scope itself is not a token scope. This is the expected default behavior.
6. **Admin API requires the token to have been issued for the `admin-cli` client** with appropriate scopes. The token was issued for `admin-cli` but the admin namespace check uses `realm_access.roles` which IS present in the token.

**Investigation result:** The `admin-cli` client is configured with:
- `standardFlowEnabled: true`
- `directAccessGrantsEnabled: true` (password grant)
- `publicClient: false`
- Redirect URIs: `http://localhost/*` (for admin console testing)

The admin user has the `admin` role which grants access to the `/admin` namespace. The token includes `realm_access.roles: admin`. The 401 on `/admin/master/console/` suggests the admin console login flow's `prompt=none` check might be using a different client or the admin console client (`security-admin-console`) is missing from the token's issued client list.

**Next steps:**
- Check if `security-admin-console` client has `directAccessGrantsEnabled` and correct redirect URIs
- Test admin console login with explicit `admin-cli` token
- Check if the admin console's `createLoginUrl` flow includes the `roles` scope properly

## Keycloak Admin Password Reset (2026-07-31 ~17:45 UTC)

**Root cause:** The admin user's password in Keycloak was out of sync with the bootstrap password "y4pp1ngb0y".
- The admin user had a local argon2 password credential (created May 23, 13:55:53)
- The password "y4pp1ngb0y" was set during initial setup via `KC_BOOTSTRAP_ADMIN_PASSWORD`
- However, the password hash in Keycloak's database didn't match "y4pp1ngb0y"
- This caused all admin API calls to return 401/403

**Fix:** Reset the admin password using `kcadm.sh set-password`:
```bash
kubectl exec keycloak-5fc7cfcb59-zkp2j -n identity -- bash -c "
  /opt/keycloak/bin/kcadm.sh config credentials --server http://localhost:8080 --realm master --user admin --password 'y4pp1ngb0y' 2>&1
  /opt/keycloak/bin/kcadm.sh set-password --username admin --new-password 'y4pp1ngb0y' 2>&1
"
```

**Verification:**
- Admin API calls now work: `kcadm.sh get realms` returns all realms
- Admin console loads at `http://127.0.0.1:8080/admin/master/console/` (returns 200)
- Admin user can authenticate with password "y4pp1ngb0y"

**Note:** The `roles` client scope's `include.in.token.scope` is set to `true` (updated earlier), which means `realm_access.roles` is now included in tokens.
